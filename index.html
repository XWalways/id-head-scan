一台主机，不止一个入口

IP 地址帮助数据包找到主机，端口帮助 TCP 把数据交给相应的应用。端口扫描要回答的第一个问题是：这个入口有没有服务在监听？

一台示例主机
192.0.2.10
→
22 / TCP常用于 SSH 远程登录
80 / TCP常用于 HTTP 网页服务
443 / TCP常用于 HTTPS 网页服务

可以把主机想成一栋楼，端口是服务窗口。但“端口号”只是约定：443 开放不等于一定运行 HTTPS，更不等于存在漏洞。端口字段是 16 位，编号为 0-65535（0 为保留端口）。TCP 与 UDP 的端口空间也各自独立。

开放 open
在当前探测条件下，有应用接受连接。
关闭 closed
探测可到达，但该端口没有应用监听。
被过滤 filtered
探测或应答被拦截，无法确定是否开放。
没有应答 ≠ 一个确定答案
也可能是丢包、延迟或主机不可达，需要结合扫描方法判断。

三次握手：先认识正常的连接

客户端先说“想连接”，服务端确认并提出自己的初始序列号，客户端再确认。第三个 ACK 到达后，服务端才完成这次连接建立。

扫描利用的，就是“连接尚未完成时，主机会怎样回答”。

开放端口收到正常 SYN 会回 SYN|ACK；关闭端口通常回 RST|ACK。后面的不同扫描，就是改变发出的报文，再观察应答的差别。

依据：RFC 9293 §3.5 连接建立；Nmap：端口状态。本文示例地址使用文档保留网段，不代表真实扫描目标。

看懂首部，才不会认错 ID

一个 TCP 段装在 IP 数据包里。IP 首部处理网络层的信息，TCP 首部处理连接、序列与端口。它们紧挨着，却不是同一层。

六个经典标志位，是六种不同的意思

每个标志位只有 0 和 1，但可同时置位。SYN|ACK、SYN+ACK 和 SYN/ACK 在这里都表示 SYN、ACK 同时为 1。

SYN：同步初始序列号

用于发起连接并交换初始序列号。正常握手的第一包带 SYN，第二包同时带 SYN 和 ACK。SYN 本身占用一个序列号。

扫描关联：SYN 扫描用它询问“这个端口愿意建立连接吗？”

ACK
确认号字段有效。它不是“端口开放”的通用证明。
RST
重置连接或拒绝不合适的报文；收到未经请求的 RST 通常不再回 RST。
FIN
发送方已没有更多数据要发送，正常关闭中用于结束一个方向的发送。FIN 占用一个序列号。
PSH
请求接收端推进数据交付；它不代表网络优先转发，也不定义应用消息边界。
URG
紧急指针字段有效，不表示整个包获得网络层高优先级。

依据：RFC 9293 §3.1 首部格式、RFC 791 IPv4 首部。这里聚焦经典六位；现代 TCP 还有 ECE、CWR 等扩展控制位，并非总共只有六位。

同样是 SYN，问法决定答案

先看最直接的方式：向目标端口发 SYN，观察它是否愿意继续握手。再看一个容易混淆的情况：如果一上来就发送 SYN|ACK 呢？

SYN 扫描：拿到第二次握手，就够了

目标返回 SYN|ACK，已经足以说明端口愿意建立连接。扫描端接着发 RST 终止这次尝试，不发送完成握手的第三个 ACK，所以也叫半连接扫描。

另外两种结果：关闭端口对 SYN 返回 RST，判为 closed；反复探测仍无应答，或收到指定 ICMP 不可达错误，Nmap 判为 filtered。

依据：Nmap：TCP SYN Scan。过滤是当前探测视角的结果；一次超时不能证明一定存在防火墙。

SYN|ACK 探测：没有先打招呼，就直接确认？

正常情况下，SYN|ACK 是对 SYN 的回答。如果目标端口并没有与探测方建立对应连接，却突然收到 SYN|ACK，其中的 ACK 就没有可确认的连接上下文。

按 TCP 规则，在 LISTEN 或 CLOSED 状态下，都应对这种报文返回 RST。

因此，不能把“RST = 关闭、无响应 = 开放”当作 SYN|ACK 扫描的普遍判定规则。

但这个特性正好可以做另一件事：让第三方主机发出一个 RST，然后读取那个 IPv4 包的 IP ID。这是理解 ID 头扫描的下一块拼图。Nmap 可自定义 SYN|ACK 标志组合，但没有一个独立的“可靠判断开放”的 SYN|ACK 扫描模式。

依据：RFC 9293：CLOSED 状态、LISTEN 状态；Nmap 自定义标志位及响应解释。

ID 头扫描：答案藏在第三方的发包里

也叫 IP ID 空闲扫描（Idle Scan，Nmap -sI）。扫描器不直接接收目标的 TCP 应答，而是看第三方主机有没有因此多发一个包。

目标不告诉 A 答案，
但 Z 的计数变化，可能泄露这个答案。

多一次发包 → 多用掉一个 IP ID

仅对本文的理想模型成立：Z 在相关出站包之间共享一个全局计数器，每发一包加 1，期间没有无关通信。IP 协议并不要求所有设备采用这种分配方式。

这就是旁信道：不读取目标应答本身，而读取它带来的另一个可观测变化。这里的变化是 Z 发出的 IPv4 报文中的 16 位 Identification 字段。

先认识三位参与者

A：扫描器
先后探测 Z，读取两次 IP ID；同时向 T 发送源地址写成 Z 的 SYN。
Z：第三方主机
IP ID 全局递增且足够空闲。常称“僵尸主机”，但不意味着已被植入恶意程序。
T：目标
它以为 SYN 来自 Z，于是把 SYN|ACK 或 RST 发给 Z，而非 A。
为什么不用控制 Z？
Z 只是在按自己的协议栈回答或丢弃报文；它通常不知道自己正在参与扫描。

    开放端口：完整流程

    先读取 Z 回给 A 的 IP ID=1000。T 向 Z 回 SYN|ACK，使 Z 额外向 T 发出一个 RST（ID=1001）。A 再次探测 Z，读到 ID=1002。

    在全局递增且没有背景流量的前提下，差值 2 支持端口开放。

    示例值均用于教学。虚线报文与中间 ID 由图解展示，实际扫描器 A 不会直接收到 Z 与 T 之间的这些包。图中不是“通过 Z 转发 SYN”：SYN 由 A 直接发往 T，只是 IP 源地址字段伪装成 Z。

    为什么开放加 2，关闭却只加 1？

    Δ = 2

    开放情景：Z 多回了一个 RST。

    T 回来的 SYN|ACK 不对应 Z 发起的连接，Z 就回 RST。这个额外发包用掉 1001；再次向 A 回包时，才用到 1002。

    Δ = 1

    关闭/静默过滤：Z 没有额外发包。

    关闭时 T 回 RST，Z 忽略它；静默过滤时 Z 什么都没收到。两种情况下，再次探测的应答都直接用到 1001。

    别忘了，第二次测量本身也会消耗一个 ID。因此基线是加 1；开放情景比基线再多 1，才得到加 2。不是“Z 收到 SYN|ACK，IP ID 自动加 1”，而是“Z 因此发出 RST，用掉一个 ID”。

    Δ = 1 的准确结论是 closed|filtered。

    它无法区分“目标端口关闭”和“路径把探测静默丢掉”。结果还体现 Z 这一来源身份所对应的访问路径与策略，不能直接等同于 A 自己连接 T 的结果。

    这个推断成立，需要哪些前提？

    同一个全局计数器

    Z 发往 A 与 T 的相关 IPv4 包必须共享可预测的递增序列。若按目的地址分别计数，中间发给 T 的包就不会改变 A 读到的序列。

    足够空闲、测量窗口干净

    Z 的无关通信也会消耗 ID。一个背景包就可能把本应为 1 的差值变成 2，制造“看似开放”的假象。

    所需报文都能到达

    A 需要能探测 Z；目标的应答需要到达 Z；Z 的反应也不能被中间设备改写成另一种行为。丢包、限速与重传会扰乱简单模型。

    伪造的源地址能通过网络

    A 发往 T 的 SYN 必须允许把来源写为 Z。源地址校验与反欺骗过滤可以阻止这一环节，设备不支持时整个推断无法成立。

    差值大于 2，或者刚好等于 2，但有背景流量怎么办？

    大于 2 说明两次观测间出现了更多发包，可能来自无关通信、重传或不适合的 ID 分配方式。不能直接判开放；应把这次结果视为不确定，并重新验证测量条件。

    “恰好等于 2”也不是免检证明。上方“背景干扰”情景刻意让目标关闭，同时插入一个 Z 发往其他主机的背景包。最终差值也是 2，但根本没有证明目标开放。

    16 位 IP ID 到顶后，会不会算错？

    会回绕。应按模 65536 计算：Δ = (第二次 ID - 第一次 ID + 65536) % 65536。例如 65535 → 0 是加 1，65535 → 1 是加 2。这仍以前提可靠、测量间隔没有跨过完整一轮为基础。

    为什么现在不能假定每台主机都适合？IPv6 呢？

    IP ID 不是一个必须逐包增长的“总发包计数器”。RFC 6864 将其语义限定于分片重组；对禁止继续分片且尚未分片的原子数据报，其 ID 可以是任意值。固定、随机或分组计数等行为，都可能让经典模型失效。

    IPv6 基础首部没有同样的 IPv4 Identification 字段；分片信息属于另设的分片扩展首部。这里讲的 IPv4 IP ID 空闲扫描不能直接照搬到 IPv6。

    是不是完全无法发现这种扫描？

    不是。目标侧通常看到来源为 Z 的 SYN，但其他观测点仍可能看到 A 对 Z 的探测、伪造流量或异常的半开连接模式。检测设备、跨点日志关联和反欺骗过滤依然有效。“不完成握手”或“没有使用自己的源地址”都不等于不可检测。

    依据：Nmap：TCP Idle Scan 原理、流程与前提；RFC 6864：IPv4 ID 字段的语义边界；RFC 8200：IPv6 首部。交互图是单端口、单位步长的教学模型；实际工具会进一步处理批量探测、重试与噪声。

    换一种问法，还能知道什么？

    扫描方式不是“更隐蔽”的等级表。每种方式发出的包不同，依赖的协议行为不同，能支持的结论也不同。

    全连接扫描 -sT

    通过操作系统的 connect() 尝试建立连接。开放时完成三次握手，再关闭连接；通常不需要自己构造原始 TCP 包。

    半连接扫描 -sS

    也就是前面的 SYN 扫描。收到 SYN|ACK 即得出开放结论，用 RST 结束尝试，不完成第三次握手。

    依据：Nmap：TCP Connect Scan；TCP SYN Scan。

    NULL、FIN、XMAS：三个包，同一种判读逻辑

    在相应协议行为成立时，监听端口会丢弃这些没有 SYN、RST、ACK 的报文，关闭端口则返回 RST。这不是“协议没规定的空子”，而是利用不同状态下处理规则的不对称。

    NULL

    -sN
    UAPRSF

    不设置任何 TCP 标志位。

    FIN

    -sF
    UAPRSF

    仅设置 FIN。不是一次正常的挥手流程。

    XMAS

    -sX
    UAPRSF

    设置 FIN、PSH、URG，并非六位全置 1。

    依据：Nmap：TCP FIN、NULL、Xmas Scans。

    ACK 扫描：测可达性，不直接测开放

    向没有对应连接的目标端口发送 ACK。未被过滤时，监听与关闭端口通常都回 RST，因此 Nmap 标为 unfiltered。它说明这种 ACK 探测能获得应答，不说明有服务在监听。

    依据：Nmap：TCP ACK Scan。

    把“观察”与“结论”放在一起

    先确认用了哪种探测，再解释同一个 RST 或同一次沉默。扫描状态属于当前方法与观测路径，不是端口永久不变的标签。

    最容易记反的四件事

    “半连接扫描”和“SYN 扫描”是两种方法吗？

    在本文与 Nmap 的常用语境下，它们指同一种方法：发送 SYN，收到 SYN|ACK 后用 RST 结束，不完成三次握手。无需把它们记成两个不同报文机制。

    收到 RST，就一定说明端口关闭吗？

    要看发了什么。对 SYN 的 RST 是关闭的重要证据；对无连接 ACK 或 SYN|ACK 的 RST，监听端口也可能按规则返回。因此必须把应答与原始探测、连接状态放在一起解释。

    NULL 就是一个“没有任何内容”的空包吗？

    不是。NULL 扫描只说明 TCP 标志位为零。IP 首部、TCP 源/目的端口和其他必要字段仍然存在；它不是没有首部的包，也不等于没有网络意义。

    “开放”和“可被利用”能画等号吗？

    不能。开放表示服务接受相应连接；是否存在可利用问题，还取决于应用、版本、配置、认证和其他条件。端口扫描提供暴露面的线索，不代替漏洞验证。
